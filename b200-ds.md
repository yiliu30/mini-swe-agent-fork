# DeepSeek Server Access On This Node

This node serves `DeepSeek-V4-Flash` behind a local OpenAI-compatible vLLM API.

## Endpoint

- API base: `http://127.0.0.1:8000/v1`
- Model path: `/storage/yiliu7/deepseek-ai/DeepSeek-V4-Flash/`
- Container: `vllm-ds-precompiled-smoke`

The server is bound to `127.0.0.1`, so direct access is from this node only unless you add SSH port forwarding.

## Required Server Mode

The server must always run with funnel top-k enabled:

```bash
VLLM_SPARSE_INDEXER_PREFILL_TOPK_BACKEND=funnel_dense
VLLM_SPARSE_INDEXER_PREFILL_TOPK_FUNNEL_MODE=turbo
```

This is enforced by the local helper in `src/minisweagent/run/utilities/deepseek_local.py`.

## Health Check

Use the built-in checker:

```bash
PYTHONPATH=src /home/yiliu7/workspace/venvs/omni/bin/python \
  -m minisweagent.run.utilities.mini_extra deepseek-local check
```

This verifies:

- one matching vLLM process is running
- `/v1/models` returns `200`
- `/v1/chat/completions` returns `200`
- tool calling works
- the audit log shows turbo funnel usage

## Restart And Re-Verify

If the server is missing or unhealthy:

```bash
PYTHONPATH=src /home/yiliu7/workspace/venvs/omni/bin/python \
  -m minisweagent.run.utilities.mini_extra deepseek-local ensure-server
```

That command:

- kills stale DeepSeek vLLM processes in `vllm-ds-precompiled-smoke`
- restarts the server with `funnel_dense` and `turbo`
- waits for `http://127.0.0.1:8000/v1/models`
- runs the health check again

## Container Introspection

Check the serving container:

```bash
docker ps --format '{{.Names}}\t{{.Status}}' | rg '^vllm-ds-precompiled-smoke'
```

Inspect the active vLLM process:

```bash
docker exec vllm-ds-precompiled-smoke bash -lc \
  "ps -ef | rg 'vllm serve|DeepSeek-V4-Flash' | rg -v rg"
```

## Access From Another Machine

Because the API listens on `127.0.0.1`, use SSH port forwarding:

```bash
ssh -L 8000:127.0.0.1:8000 <user>@<node>
```

Then call:

```bash
curl http://127.0.0.1:8000/v1/models
```

from your local machine.

## Current Caveat

The node currently has severe Docker root disk pressure on `/`, while model storage is on `/storage`. If large uncached SWE-bench runs fail with Docker `125` or startup timeouts, the immediate cause is usually Docker data living on `/dataset/docker`, not the DeepSeek API itself.
